# NextComp briefing for Tibo and agent reviewers

This is the full briefing selected after testing seven descriptions. It invites inspection of the working system and versioned evidence; it does not predict the recipient’s interest. The [capability map](CAPABILITIES.md) supplies the source trail, and the [evaluation record](BRIEF-EVALUATION.md) explains how the drafts were tested. No outreach has been sent.

NextComp is how we keep using our own computing environment when we are away from it. We can speak or type an ordinary intention from Android, have stock Codex work where the relevant files, applications and tools already live, and remain part of the work without being at a desk. It is an open-source alpha built for one owner and their trusted devices, with a self-hosted backend and access to their existing execution environments.

What matters to the user is the ability to do things: investigate a question, diagnose a machine, continue a software or creative project, act on an intermediate finding, ask a follow-up while other work continues, and operate the phone itself when its accessibility tools are enabled. These possibilities inherit the actual capabilities and constraints of the selected environment. New tasks default to the owner's full-permissions preference; the coordinator's small/read-only-task role is a behavioral instruction, not an enforced read-only sandbox when full permissions are enabled. NextComp does not ship a rendering engine or invent new underlying agent intelligence. The user's Linux tools and projects, stock Codex skills and integrations, and optional phone-local Termux/accessibility environment are what make the work possible.

There is a coordinator because the person should be able to say what they want without always remembering a session or command. It can do a quick read-only inspection and answer there. For sustained work it can discover, create and continue real sessions. The user can also address a session directly. They can read useful answers before the final response, reply to those answers, jump to their context, steer active work, queue something for later, interrupt, respond to supported questions and approvals, and choose the execution profile. The point is retaining agency over work already in motion, not watching a wall of terminals.

The Android experience carries that into everyday use. Voice is manually controlled recorded turns with transcription, Codex coordination and synthesized replies; text remains available. Notifications can convey work needing attention and accept replies. Session activity and useful context remain visible on the list. A phone can be the place the person gives an instruction and also, with stock Codex in Termux and separately enabled accessibility, the place the work executes. Optional inline Italian immersion changes selected phrases in the same content flow, with text taps restoring the source in place.

A useful demonstration would follow one person's actual request across these surfaces: a short machine question answered in coordinator chat; sustained work continued in a session; an intermediate result replied to while another task continues; then an actionable notification and continuation from the phone. That demonstration should include interruptions and reconnects. We are not presenting this illustrative sequence as already fully qualified, or claiming every task is safe or feasible without looking.

The implementation is public: [FallSoftCo/pocket](https://github.com/FallSoftCo/pocket). Stock Codex app-server powers the sessions; a self-hosted backend connects through trusted HTTPS/WebSocket, with Tailscale recommended. Firebase carries notification titles and bounded previews. Voice uses the compatible stock Codex native WebRTC transport with the host's ChatGPT authentication; it does not require a separate audio API key. Native voice and task-model usage are distinct, and availability depends on the account and CLI. Notification speech also has an offline Android path. Alpha21 has backend and Android tests, signed builds and emulator interaction qualification. At the 2026-10-05 delivery check, the physical phone was independently confirmed on alpha20; its alpha21 install was blocked by a disconnected Accessibility bridge. Recurrent phone-network symptoms need further qualification. Those limitations affect release confidence, not the scope of computing the interface is intended to make accessible.

We would like Tibo or his agent to inspect what this changes about the human side of personal-agent computing: how much intent and context a person must repeat, when they need to look at a screen, what remains useful before the final answer, and how control passes between phone, coordinator and working session. The first ask is feedback on a real demonstration and the session/control architecture. There is inspectable machinery behind the description: [voice-controller.mjs](../server/voice-controller.mjs) persists coordinator identity and selected session per device, implements explicit session actions, and records turn/tool-call identities to handle duplicate delivery and uncertain outcomes. [native-voice.mjs](../server/native-voice.mjs) separates the audio-only transport from task execution. The qualification records support particular observations, not all use cases: delayed session discovery was investigated against real existing threads; a real teacher response qualified inline replacements; phone-local alpha20 source synchronization preserved protected state while leaving its daemon stopped. See the [capability and evidence map](CAPABILITIES.md) for inspectable paths and their limits. Integration with Dots may be worth exploring afterwards, but is not a prerequisite for understanding or using NextComp.

Concrete runtime evidence matters more than enumerating controls. The public [verification record](VERIFICATION.md) contains historical live checks that should accompany this submission, clearly labeled by version:

- In phone-local alpha1, the physical Pixel paired through loopback, listed its real Codex sessions, and completed a real stock Codex turn creating and reading a local proof file. The separately enabled accessibility service reported the foreground app, produced a valid screenshot, performed Android Home navigation, and then reported the launcher. A model called phone_screen and completed with the actual foreground package. These are direct on-device execution/inspection observations, not just a planned Termux architecture.
- In alpha2, a real phone-local model turn again used the configured phone_screen tool and returned the correct foreground package after accessibility recovery. The record distinguishes the system accessibility gate from the independent app permission switch.
- An earlier fresh-environment exercise cloned public source into a new Linux container with only the owner's Codex authentication, configured a separate Firebase sender and paired a clean Android emulator. It started work from the app and received completion, answered a live command approval that produced the expected test file, replied through a notification into an idle session and received the continuation, delivered FCM with the app process absent, and stopped a running task. This is historical automated end-to-end evidence, not a current-release new-user study.
- Earlier physical checks followed a conversation with over 500 rows and successfully replied to an active Codex turn through a notification. Resumable notification speech was checked on the physical phone, including preserving a saved playback position across an update and a temporary audio-focus interruption. These older offline-speech observations should not be presented as qualification of current native voice quality or current networking reliability.

These observations demonstrate implemented paths into a person's computing environment and back, including work performed on the phone. They do not establish arbitrary creative application proficiency, complete eyes-free exception handling, current alpha21 delivery or a comparative usability advantage. A reviewer should inspect the versioned records and implementation, then ask for a current live demonstration of the particular behavior they care about. The proposal is an interaction system already used across real execution environments, with bounded proof and unresolved release-level issues.

## Proposed technical conversation

We would like to show the actual workflow and discuss three questions: how a persistent personal agent should delegate into existing stock Codex sessions; how intermediate findings, decisions and notifications should stay actionable without requiring continuous supervision; and what Android execution adds when the phone is more than a remote display. We can then discuss whether a supported Dots integration would be useful. This repository provides the context for that conversation without requiring access to our private deployment.

Official documentation already describes [remote task control](https://learn.chatgpt.com/docs/remote-connections), [Dots using connected computers](https://learn.chatgpt.com/docs/dots/computers-and-apps) and [conversation/call channels](https://learn.chatgpt.com/docs/dots/channels). We do not claim those general capabilities are exclusive to NextComp. The contribution to evaluate is the particular interaction system and its behavior in actual use.
