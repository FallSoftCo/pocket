# Web and Android parity

Requested 2026-10-19. Android source 0fdd2ed and the deployed tailnet web sign-in are the baseline; the web client previously remained on the October 8 implementation.

Parity means the same operation/receipt semantics and useful information with browser-appropriate controls, not claiming Android hardware key interception or closed-browser push. Existing pairing, browser drafts, outgoing IDs and unknown receipts must survive.

Delivery order:
1. Codex current-head/history ordering, loading at the reading edge, bounded automatic earlier loading driven by reader intent; retained local content and independent latest/history reads.
2. Dense live session cards, clear idle hue without opacity, exact-text rename and child badge; consistent bottom controls and account usage with honest freshness.
3. Fold every contiguous operation/wait into expandable runs, readable Markdown/tables/inline images, notes as an actionable conversation filter, questions/approvals and controllable notification behavior.
4. Explicit speech, durable independent recordings with immutable destination, one click start/stop-and-send, cancellation, ten-minute capture where backend supports it, 0/50/100 playback volume.
5. Native transgrammatic English/Italian plans and authored interface lexicon, line-by-line shared reading wave with no animation-driven application state updates.
6. Room feeds and actions using the existing viewer-bound independent conversation/activity API, truthful room activity, explicit direct recipients and exact accepted receipts. Named environments require gateway and device-authority scoping; never substitute remote tokens or overwrite the current phone profile.

Browser limits to keep explicit: physical volume keys are normally intercepted by the OS; browser shortcuts and an on-screen recording control remain necessary. Background tabs/closed browsers do not have Android FCM delivery or native keep-awake guarantees. Current live backend capabilities determine available voice and room adapters.

Each delivered portion needs rendered desktop/touch journeys, real read-only private-gateway verification, synthetic isolated writes only, and source/release receipts. Do not start real work for QA or turn every helper into a new unit suite.
