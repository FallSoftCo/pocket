# Pocodex Maintainer operations

This optional Linux worker implements [the contribution policy](../MAINTAINER_POLICY.md). It subscribes to signed GitHub webhooks, reviews immutable PR snapshots with the owner's existing Codex login, and dispatches the trusted main-branch workflow. PR changes and completed CI runs trigger work; an empty queue has no timer, GitHub polling, or model calls. Public comments and the required `Pocodex review` check come from GitHub's built-in Actions App, `github-actions[bot]`. Approval is recorded as a successful check rather than a formal PR approval, so this works even when organization policy prohibits approving reviews from Actions. There is no hosted FallSoft review service. Codex credentials are never stored in Actions; an optional independent health monitor has a separate push-only Firebase credential.

## Decision and trust boundaries

- Automatic merging covers suitable implementation changes, including dependencies and sensitive code, after two independent approving reviews without findings. Both `backend` and `android` checks must pass. Small prose edits (at most 120 changed lines in README.md or docs/DEPLOYMENT.md without commands, links, directives, or sensitive terminology) can qualify with one low-risk review. The worker cannot approve changes to its own policy, authority, or CI.
- A scope rejection requires two fresh reviews agreeing on an explicit rule, each with quotes verified against added lines. The bot explains the decision and suggests a fork. Model judgments can be wrong; maintainers can override them.
- Missing files, binary changes, renames, more than 20 files, more than 600 changed lines, or more than 160 KB of context go to the owner. Suspected secrets are not quoted. This is a precaution, not a complete secret scanner.
- Review context includes the policy from the trusted base commit and changed files as text. PR descriptions and files are untrusted. Only authorized `/pocket reconsider <reason>` comments enter the review as untrusted evidence, never instructions. Reopening a PR or changing its commit, base, title, body, or policy requires reconsideration.
- The reviewer runs inside Bubblewrap with a minimal filesystem and a copied Codex login. It has no GitHub/Pocodex credential, shell, repository checkout, user configuration, plugin, or executable tool host. Execution, browsing, agents, and integrations are disabled. CLI tool declarations may still be advertised; execution fails closed, and non-text action events invalidate the result. Outbound networking remains available for Codex authentication/inference. This is not a general sandbox for running contributor code.
- The privileged Actions job checks out only trusted `main`. It recomputes the policy decision and snapshot digest, checks for holds and changed revisions, and merges with GitHub's expected-head SHA. GitHub branch protection requires CI plus a successful commit-bound `Pocodex review` check from the Actions App. Closing uses a fresh snapshot check, but GitHub's close API has no atomic expected-head parameter.
- After approving a contribution, the controller can approve its pending fork CI run only when `.github/` is unchanged. It can update an out-of-date branch when the contributor allows maintainer edits; the new commit then needs fresh review and CI. Conflicts and branches that cannot be updated stay open. Contributor tests run only on GitHub's temporary CI runners with a read-only token, never on the review workstation.
- The controller has GitHub write/dispatch access. Keep its code, config, cache, and login private and owner-writable only. Do not run it from an untrusted development checkout. GitHub Actions logs contain the public decision, not the reviewer's login. Review content is sent to the configured OpenAI model under the owner's account.

## Installation

Requirements: Linux user namespaces, `bwrap`, Node 22.13+, a repository-scoped GitHub App installation (or a temporary `gh auth login` for bootstrap), and authenticated **Codex CLI 0.157.1**. The isolation adapter rejects other CLI versions until revalidated. The default model is `gpt-6-astra`; set `reviewer.model` to an available model if necessary. Review usage counts against the owner's Codex account. The default cap is 20 inference calls per UTC day, including corroborating reviews and failed attempts.

On hosts where AppArmor restricts unprivileged user namespaces, give the worker's root-owned Bubblewrap binary an explicit user-namespace profile instead of disabling the host restriction. `reviewer.bubblewrap` can select that dedicated binary; the default is `/usr/bin/bwrap`.

1. Install this code from a trusted revision into a private directory outside contributor worktrees. Copy `maintainer/` there; no npm dependencies are needed.
2. Create private configuration using [the example](../maintainer/config.example.json). Expand all paths to absolute paths. Review and runtime-error notifications default to off (`notifyReviews` and `notifyErrors`). `pocket` is optional; its thread must be an existing owner-controlled Codex conversation. If enabled, escalations include the PR link and reviewed commit. Respond in GitHub, or ask your trusted Codex session to handle the linked PR; the worker does not interpret phone replies as merge authorization.
3. Publish `maintainer/`, MAINTAINER_POLICY.md, and `.github/workflows/maintainer.yml` on the repository's default branch. This initial distribution targets `FallSoftCo/pocodex`; a fork must deliberately update the repository identity in the adapter, workflow guard, and policy.
4. Configure main-branch protection: require successful `backend`, `android`, and `Pocodex review` checks from the GitHub Actions App, and require branches up to date. Do not give the Actions bot a bypass. Formal approving PR reviews are not required; `Pocodex review` supplies the automatic review gate. The default workflow token remains read-only and organization settings need not permit Actions approval reviews.
5. Create labels `maintainer:hold`, `maintainer:owner`, `maintainer:changes`, `maintainer:out-of-scope`, and `maintainer:ready`.
6. Generate a private webhook secret (at least 32 random bytes) at `webhook.secretFile`, and set `webhook.repositoryId` to the repository's numeric GitHub ID. Adapt the [service](../deploy/pocket-maintainer.service.example) into your user systemd directory. Run once with `dryRun: true`, inspect the result, then set it to false and enable the service. When upgrading from the polling version, stop and disable `pocket-maintainer.timer` and remove its unit file.
7. Expose only the webhook listener through an HTTPS reverse proxy. It binds `127.0.0.1:18881`, accepts signed `POST /github/events` and exposes a minimal `GET /healthz`, validates HMAC-SHA256 over the raw body, checks the repository ID, and durably queues identifiers before acknowledging. It has no app, transcript, file-serving, or administration routes. Keep Pocodex's main port private.
8. Register the subscription with `node maintainer/register-webhook.mjs https://YOUR_WEBHOOK_HOST/github/events`. This creates or updates the matching repository webhook for `pull_request`, `issue_comment`, `workflow_run`, and `push`; the secret is read from the private config path and never printed. An HTTPS proxy on a dedicated port is supported. For example, a separate Tailscale Funnel on port 10000 can route to this listener; never turn on Funnel for the Pocodex application port.

GitHub's [webhook signature guidance](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries) explains authentication. A dedicated [Tailscale Funnel](https://tailscale.com/docs/reference/tailscale-cli/funnel) is one optional HTTPS transport; any suitable reverse proxy works.

### GitHub App credential

Use a private GitHub App installed on **only this repository**, with read/write contents, pull requests, issues, Actions, and repository webhooks; no organization permissions. Its App webhook can remain disabled because the existing repository webhook handles delivery. Configure `githubApp` with `appId`, `installationId`, `repositoryId`, and an absolute `privateKeyFile` outside the checkout. Installation tokens are restricted to that repository, refreshed before expiry, and never given to the reviewer. Once configured, App authentication failures never fall back to a personal token.

`register-app.mjs` provides a two-hour, single-use manifest registration flow. Set `MAINTAINER_CONFIG` and `MAINTAINER_SETUP_ORIGIN` to the dedicated HTTPS origin, proxy `/setup/` to loopback port 18882 with access logging disabled, and run the helper. The private config directory receives `github-app-setup-url`. Open that URL while signed into the repository organization, create the private App and select only Pocodex. The callback stores the key privately and verifies the installation before updating config. Restart the worker, verify App authentication, remove the old `GH_TOKEN` environment file, then stop the helper and remove its temporary proxy route. The bundled manifest targets FallSoftCo; forks must deliberately adapt the identity.

For bootstrap only, an unconfigured controller can use `GH_TOKEN` or `gh auth token`. Never publish credentials. The review subprocess receives only its separate Codex login.

### Contributor reconsideration

A PR author or current collaborator with write access can comment `/pocket reconsider <reason>` (maximum 4,000 characters). The first three authorized clarification comments per PR enter the immutable snapshot. Editing them also invalidates the old review. Ordinary comments and unauthorized commands do not trigger reviews. The worker acknowledges the request and can reopen a PR it declined; it never reopens a merged, held, or human-closed PR. Existing policy, budget and CI gates still apply. GitHub's reopen API has no atomic revision precondition, so the controller rechecks state before writing.

### Failure alerts and transport recovery

Keep `notifyReviews: false`. Set `notifyErrors: true` and configure `alerts.credentialsFile` plus `alerts.targetsFile` for operational failures. Use a separate Firebase service account with only `cloudmessaging.messages.create`; the target file is a private JSON array of `{device_id, token}` for the owner's paired phone. Alerts go directly through FCM, without requiring the workstation or Pocodex backend to be online. A successful alert is deduplicated for six hours per incident. Invalid/rotated device tokens require refreshing this private target file and the monitor secret; revoking a device also requires removing it from both. No conversational reply is offered for these operations alerts; tapping opens GitHub Actions.

Install the recovery service and timer examples for the same dedicated worker account. Every 15 minutes they inspect **failed webhook delivery records**, not PRs, and ask GitHub to redeliver missed events. Exact 64-bit delivery IDs are preserved; successful redeliveries are skipped. GitHub retains only three days of delivery history. The audit is bounded at 1,000 records and 20 redeliveries per invocation; exceeding the history bound fails visibly. A service restart also reconciles currently open PRs. After an outage longer than the delivery retention window, inspect merged PRs and request any missing post-merge checks manually.

Expose `/healthz` through the dedicated HTTPS proxy. It returns only healthy/unhealthy, including dead or repeatedly failing queued work and failed or stale delivery recovery (45 minutes without a successful audit). The `Maintainer health` Actions workflow checks it every 15 minutes from outside the host, with no PR scans or model calls. Set repository variable `MAINTAINER_HEALTH_URL`, and secrets `MAINTAINER_FIREBASE_CREDENTIALS` (the separate push-only account JSON) and `MAINTAINER_ALERT_TARGETS` (the target array). It alerts on a newly observed outage and at most once per UTC day during a continuous outage. GitHub scheduled workflows may be delayed, so this is best-effort monitoring rather than a strict uptime SLA.

### Post-merge verification

A merged-PR event durably queues a `check.yml` dispatch for the exact merge commit, including merges performed by Actions. Both backend and Android jobs check out that commit with a read-only token. Dispatch receipts and matching run titles avoid repeated runs; a failure sends an operational alert. Normal main-branch CI failures alert too. A failed check never silently rolls back a merge.

## Control and troubleshooting

```bash
systemctl --user status pocket-maintainer.service
journalctl --user -u pocket-maintainer.service -n 50
systemctl --user stop pocket-maintainer.service
```

Apply `maintainer:hold` before editing or manually deciding a PR to pause pending automatic actions. Disabling the GitHub `Pocodex Maintainer` workflow also prevents queued dispatches from acting. Stopping the listener alone does not cancel an already-running Actions job. To resume, remove the hold or start the service again.

The listener stores delivery IDs, payload digests, and a coalescing work queue in private SQLite. Duplicate deliveries do not repeat work; events arriving during a review remain queued. PR changes target that PR. CI completion triggers the merge decision immediately. Main-branch changes and completed maintainer actions reconcile open PRs. Bot labels/comments and unrelated workflows do not create review loops.

There is no recurring PR scan. Accepted work survives restart. GitHub [does not automatically redeliver failed deliveries](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries); the separate recovery timer requests redelivery. The independent health workflow alerts when the host cannot process events.

Only known outstanding work can schedule a timeout: failed jobs have six bounded backoff retries, a dispatch without a bot receipt is checked after ten minutes (at most three dispatch attempts per snapshot), and a depleted inference budget defers queued work to the next UTC day. Jobs that exhaust retries remain recorded for inspection; a new relevant event reactivates them. Failed reviews never approve anything. GitHub histories and catch-up lists above 1,000 records fail closed. Review notifications remain off by default.

Keep state outside the checkout. Never delete it casually: it records inference budgets and notification/dispatch receipts. For an independent always-on host, use a dedicated private Codex auth file and set `reviewer.persistAuth: true` so the trusted CLI can renew its login. Only refreshed credentials for the same account are saved; a concurrent external login change is never overwritten. An expired or revoked login still requires authenticating again. After changing the policy, worker, model, or CLI version, run `npm test`, validate isolation and a real review, then deploy the trusted code copy. This is deliberately a narrow initial maintainer, not an autonomous security auditor.
