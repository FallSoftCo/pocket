**State dependencies that must survive the split**

- Request secret versions 1/2, form version 3 and approval versions 4/5 share `same-native-request`. The request workflow must retain this sequence. Its accepted-answer counts 3/4 include the two earlier secret/form answers; extracting only approvals without rebuilding that baseline would silently change the evidence. Keep exact assertions or use explicit per-workflow baselines, never broad `>=` checks.
- The delayed approval comes from the actual rendered `SemanticsActions.OnClick` callback. It is checked on another source with the same thread ID, another thread on Alpha, then against a replacement token/action index on the original thread. Do not substitute a direct delivery-helper call, manually constructed decision, new ID, or unrelated environment.
- Closing the resolved decision drawer currently leads directly into the canonical Runs/output UI (lines 200–211). Preserve that cross-feature transition in workflow 1: enable the synthetic Alpha command row, wait for Runs, use `openOutput()`, verify the first Alpha page and original turn/item identity, close through the actual dialog control, then verify drafts/no reply. Workflow 2 still owns all pagination and output-failure assertions. This short deliberate overlap preserves a previously exercised transition; it is not another independent happy-path suite.
- Output mode and terminal permissions are coupled in fixture `executionFeatures` (lines 14–17): `outputMode=unavailable` also makes terminals read-only. Keep the existing reset to qualified output modes and removal of command rows (lines 235–237) **inside workflow 2 before terminal checks**. Do not remove it merely because there are now fresh cases.
- Held Alpha output must actually enter the HTTP route before navigation; release it only after Beta is selected. Preserve the absence of the old dialog, the new Beta output text and originating request checks. Keep existing condition-based waits and UI visibility assertions; do not replace them with sleeps or `runCatching` around failed clicks/scrolls.
- Workflow 2 previously ended with the Beta terminal dialog visible; workflow 3 then navigated back to Alpha. Preserve a short terminal-to-context handoff at the end of workflow 2: navigate to Alpha, assert the terminal/confirmation is absent, open Context using the real footer, verify Alpha context, then close it and check drafts. Workflow 3 owns all boundary selections and mutations. This protects dialog invalidation across feature families without carrying fixture state between cases.
- Fork recovery, subsequent revert and settings belong in one workflow. Fork recovery selects `parity-fork`; the explicit navigation back to the original Alpha thread before draft editing is essential. Do not seed a recovered receipt, select the branch directly, or replace `Check saved operation` with a raw API call. Preserve exact original ID lookup and the no-resubmission assertion.
- The final settings check is intentionally after revert while the edited draft/keyboard path has been exercised. Moving it to a clean standalone settings smoke test would lose the actual draft-preservation interaction. Settings remains read-only synthetic catalog inspection, not a configuration-write assertion.
- `calls()` reads `/_qa/state` on Alpha, but that response contains **both origins'** call log and answer log (fixture lines 13 and 57). Preserve the combined log so foreign effects remain observable. Do not filter foreign calls out before counting or clear logs after a source switch. Each fresh workflow starts with an empty fixture log and the same raw thread/process/request IDs on both authorities.

**Shared setup and failure retention**

Keep `prepare()` (lines 114–129) and the existing `menu`, `contextTools`, `navigate`, output, request and capture helpers in the same test class. A small `workflow(name) { ... }` wrapper can put `prepare()` and scenario execution inside the same failure-capture boundary, with the original exception rethrown. The present `prepare()` is outside that boundary. A capture failure must not turn a scenario failure into success. Retain the owned-emulator/explicit-loopback checks, canonical-history assertion, real footer viewport checks, measured context-sheet expansion and original source-bound preference bootstrap.

“Shared setup” means shared code, **not a shared running fixture or instrumentation process**. Each method is invoked alone as `Class#method`, with its own UUID/tokens, fresh fixture process and both sources initialized to qualified/default state. Keep the runner's existing owned-device lock, pre-existing OS-dialog admission, preference retention/restoration, fixture cleanup and original intent/no-replay behavior. Do not add a global fixture-reset endpoint or run all methods through one `am instrument -e class Class` invocation: Android `Pocket` singletons, open UI, output waiters, pending decisions and fixture operation maps are stateful, and the runner expects exactly one test result per receipt.

Screenshots/XML remain unique under `native-parity-$runId`; retain existing stage captures within their owning workflow. Name any new transition captures by workflow. Do not infer a successful native journey from compilation, HTTP fixture assertions or screenshots alone. A failed new method keeps its failed receipt/log/captures; the runner must not replay the same intent to obtain a green result.
