# NextComp on the web

The browser client reuses its paired NextComp gateway. The room candidate mounts canonical Hollywood rooms alongside retained stock sessions, with keyboard/mouse and single-column touch layouts and an installable web app manifest. Coordinator, stock-session and room identities and drafts remain distinct. Opening a delegated stock agent exposes its actual parent and permits input only when the runtime explicitly advertises direct-input support. A fork is not treated as an agent parent. Source support is not evidence that every running gateway has been updated; see the qualification boundary below.

## Private deployment

Run the gateway as the same workstation user as NextComp. It binds only to loopback and proxies ordinary paired-device requests to the existing backend. It never loads the backend's owner token. Point a **tailnet-only** Tailscale Serve HTTPS listener at it; never enable Funnel or expose either listener publicly.

```sh
WEB_ORIGIN=https://YOUR-PRIVATE-HOST:8448 \
POCKET_URL=http://127.0.0.1:18880 \
WEB_PORT=18882 node server/web-client.mjs
```

Set `WEB_DATA` to an absolute private directory to override `~/.local/share/nextcomp-web`. Its mode600 `cookie-key` preserves browser pairing across gateway restarts. Back it up privately; never include it in source or an artifact. Start with [the service example](../deploy/nextcomp-web.service.example). This separate gateway requires no Android upgrade, backend data migration or backend restart.

Pair using the ordinary one-use code from `scripts/pair-device.mjs` with the existing backend deployment environment. The browser gets a separate device identity; it does not reuse the phone's bearer. Device bearer material is kept in a signed Secure HttpOnly SameSite=Strict cookie. Pairing responses remove the bearer from JSON. Writes and WebSocket upgrades require the exact configured origin. The gateway's key authenticates its cookie; backend device revocation remains authoritative. Unpair clears the cookie and this browser's saved drafts/recording; workstation device revocation is required for a lost device.

## Interaction

- Coordinator text uses the existing device-scoped voice-controller conversation; direct text uses the session outbox. Enter sends/steers, Shift+Enter inserts a line, and the delivery selector queues later input. Ctrl/Cmd+K focuses work search.
- Drafts are isolated by paired device and conversation; room drafts additionally retain gateway/binding, recipient, audience and reply source. Durable immutable intents and request IDs are saved before sending. Reconnect reads only the original receipt at its captured route: HTTP200 alone, unknown state,404, identity/scope mismatch or refresh failure never clears the draft or silently resubmits. A minimal stock POST acknowledgement is followed by the original GET receipt and exact thread identity check. A room acknowledgement must identify the original human event, binding and target. Accepted cleanup never erases a newer edited draft. Ambiguity remains visible for explicit review, not a replacement request. Task creation has its own durable creation outbox. This is not an exactly-once guarantee.
- Room discovery uses authenticated `/web/environments` and `/api/hollywood/v3/identity`, retaining the verified `X-Hollywood-Binding` scope. A healthy federated ingress can supply the room catalog without serially scanning every host. First history explicitly requests `before=9007199254740991`; conversation/activity/all keep separate cursors while older pages stay readable through live head refreshes. Read-only failover to another verified route for the same logical room does not move drafts or captured outgoing receipts. Fresh native state, not a historical executor record, determines current room activity; expired observations become unavailable.
- Human room input defaults to public fanout, with explicit audience/recipient and contextual Reply-source controls. Questions/approvals retain their original native callback scope; expiry or failed recovery never creates another turn. Unsupported actions remain unavailable rather than borrowing a stock-session endpoint.
- The common bottom toolbar visibly shows account usage and source provenance. It uses existing source-bound status/rate-limit observations only, not a room quota service or a per-room poller. Zero, credits, reset, Last known and Unavailable remain distinct; a quota observed through a gateway is not proof of a room-wide provider account. Large text wraps controls using their caption size; quota digits and percent stay grouped and the account pane remains within the visual viewport with a reachable Close.
- Conversation rows merge by stable item IDs/revisions. Older fetched pages stay available through live refreshes and switching; paging can trigger near the top. Manual scrolling pauses following; Latest returns to current work. Important filters the same timeline. Intermediate answers retain contextual reply and explicit native speech actions.
- Work seats remain stable during metadata/preview refreshes. Refresh or returning to the touch work list can reconcile order. Work time uses normalized `recencyAt`, `activityAt`, `createdAt`; metadata `updatedAt` never makes work recent. The deployed session catalog is authoritative: the gateway passes through its work recency, parent/input capability, live status and pagination without rereading or overwriting runtime metadata. Set `WEB_LEGACY_METADATA=1` only when explicitly bridging an older backend; leave it unset with the canonical session catalog. Unsupported child history uses the existing `ThreadHistory` reader without `thread/resume` or writer ownership. Child guidance requires explicit capability, and parent navigation never moves/replays its draft.
- Supported native questions and command/file approvals use the exact pending request ID and offered decisions. Expired requests fail without being converted into a new request. Needs you filters the existing session list and opens the original work and supported request controls. The permanent Work updates feed is removed; stored reports and per-browser scheduling preferences in Settings remain. Unsupported request kinds remain terminal-only.
- Session controls include follow/unfollow, rename, interruption, queue resume, archive/restore and offered next-turn model/effort/Plan settings. Execution environments and permissions are still governed by the backend and stock Codex.

## Voice and browser limits

The voice transport adapts the existing Android `native-voice.html`: WebAudio creates a silent sender track; manually captured browser audio is buffered, then played into the native WebRTC connection after the user selects Send recording. The native backend transcribes and submits the resulting coordinator/direct turn. No account or audio API key reaches the page. Audio capture requires a supported secure browser and explicit microphone permission. Saved recordings remain privately in IndexedDB across reloads, scoped to their original conversation. Ambiguous audio delivery is held for review instead of automatically replayed. Explicit Speak starts native account playback; Stop speech closes it. Browser autoplay, account/provider availability, delayed transcription and speech quality remain qualification limits.

The manifest and icons support browser installation where available. The service worker installs without caching authenticated responses, transcripts, recordings or drafts in CacheStorage. Offline browsing/execution is not supplied. Draft editing remains local while disconnected, and delivery status distinguishes accepted requests from completed work.

Browser notifications are opt-in, generic previews while the WebSocket is connected. Background tabs may be suspended; closing the browser ends delivery. No web push, guaranteed background microphone/audio or closed-app alert delivery is claimed. Keep the Android notification return path for these cases. See [MDN installability](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable) and [background operation](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Offline_and_background_operation).

## Appearance and clean private access

Appearance is available on the pairing screen and in Settings: System, Light or Dark. System is the default and follows live OS changes. An explicit choice persists in browser storage and synchronizes across tabs, independently of pairing. Semantic colors cover conversation, code, recording, attention, errors, fields and controls; the head script selects colors before the stylesheet paints. If browser storage is blocked, the choice works for the current page.

The initial private deployment used 8448 to avoid modifying the shared 443 listener while the client assumed root paths. Standard HTTPS now supports an additive `/nextcomp/` mount, preserving the existing root, galleries and other services. This path shares the HTTPS origin with those trusted owner services; a path is not a separate origin. A dedicated Tailscale Services hostname would require additional service/control-plane configuration and was unnecessary for this deployment.

For a mounted deployment set `WEB_ORIGIN=https://YOUR-PRIVATE-HOST`, `WEB_BASE_PATH=/nextcomp/` and a separate loopback port, then add only that path with `tailscale serve --bg --https=443 --set-path=/nextcomp/ http://127.0.0.1:YOUR-PORT`. Tailscale Serve strips the mount prefix; the gateway prefixes assets and the client scopes API, attachments, WebSockets and service workers. The manifest has `/nextcomp/` identity, scope and start URL. Never enable Funnel.

Keep the old gateway URL available using the same private `WEB_DATA` signing key. Secure host cookies are not port-scoped, so an existing valid paired cookie authenticates on 443; revoked identities still fail backend authentication. Browser drafts and saved recordings are origin-scoped. Set `WEB_MIGRATION_SOURCE_ORIGIN=https://YOUR-PRIVATE-HOST:8448` on the new gateway and `WEB_MIGRATION_TARGET_ORIGIN=https://YOUR-PRIVATE-HOST` on the compatible old gateway. A narrowly permitted old-origin iframe transfers only missing app storage when its saved device identity matches the current authenticated device, with exact origins/source/nonce checks and bounded recording size. Old storage remains intact, newer destination drafts are not overwritten, and pending request IDs remain unchanged. Browser privacy restrictions or unavailable old storage can prevent transfer; the old URL remains the recovery path. Theme choices are otherwise per origin. The old page links to the clean address.

Old installed PWAs remain on the old origin. Install from the new address for the new app scope; installation support depends on the browser. No backend restart or Android pairing migration is required. Current evidence: [web-theme-access qualification](qualification/web-theme-access-2026-10-08.json). Rendered browser inspection and actual browser migration remain outstanding while the configured computer-use resource is quarantined.

## Optional automatic tailnet access

When explicitly authorized, set `WEB_TAILNET_AUTH_SECRETS` to the private backend secrets JSON on the clean gateway only. This enables automatic browser pairing through the existing `/api/pairing` and `/api/pair` contract. It does not change Android pairing or backend admission. Keep the gateway loopback-only behind private Tailscale Serve; never enable Funnel. Every browser receives its own ordinary revocable device credential in the existing Secure HttpOnly cookie. The provisioning credential is never sent to the browser.

The login POST requires the exact configured Origin and a loopback proxy connection. Its last forwarded address must be a tailnet IP independently resolved by the local `tailscale whois`; any supplied identity header must match. Tagged nodes are supported. New logins are capped at six per minute; existing paired cookies need no extra lookup. All tailnet members allowed to reach this service can operate NextComp under this explicitly enabled policy. Remove the variable and restart only the web gateway to disable automatic admission; existing device revocation remains available. Revoking a browser invalidates that credential, but the browser can sign in again while it retains tailnet access and automatic admission remains enabled. Remove tailnet access or disable automatic admission to prevent re-enrollment.
