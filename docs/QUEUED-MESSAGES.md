# Queued messages

A queued reply is a saved future input, separate from accepted transcript messages. Android and web display pending requests in the conversation with queue state and direct Steer now, edit and remove controls. Steer now targets positively verified current work; Send now starts a turn only when the native session is positively idle. Unverified status keeps promotion disabled. Held requests remain visible as paused. Sending and unknown delivery retain their existing protections.

The backend publishes one complete versioned outgoing snapshot in the existing reply event and existing admission, receipt, mutation and history responses. A per-thread SQLite revision advances transactionally with outgoing changes, including deletion. Reading revision and rows uses one savepoint. No additional endpoint, model polling or notification stream is introduced.

Clients retain this metadata under environment, backend credential identity and thread. An older history response cannot overwrite a newer outgoing snapshot or resurrect a removed request. Queue metadata does not alter canonical transcript ordering. Initial admission and sending transitions now publish their state immediately to other connected devices.

Queue dispatch first checks FIFO ownership, then reads current native thread metadata without history pages. Only current idle status permits next-turn admission; stale historical in-progress records cannot keep an idle queue stuck. Existing native busy rejection, stop/held behavior and uncertain-delivery rules remain authoritative.

Qualification uses the actual gateway, HTTP pairing, WebSocket, SQLite and process restart with a deterministic stdio provider. It checks cross-device admission/edit/removal, late history, durable revision, FIFO and no dispatch of a cancelled row. This is transport and application proof, not provider inference, physical-phone or private terminal-buffer support. Native UI and exact optimized APK evidence belong to the versioned private release receipt.

Authenticated socket reconnect also sends complete recent outbox snapshots within a bounded bootstrap budget (128 threads from the latest 512 pending rows; 256 KiB per group and 1 MiB total conservative encoded estimate). Oversized groups are omitted, never truncated or declared empty; their ordinary authenticated head remains authoritative. This sends no pushes and starts no work. Web acknowledgement and live observations both update this same source-bound state, even before a transcript page exists.

Promotion uses the existing reply mutation with `action: "send"`. Only an original next-turn message in queued or held state can become steering input; its ID, text, creation time and admission provenance remain unchanged. A repeated promotion, sending message or uncertain delivery cannot be promoted again. Explicit recovery of failed or unknown delivery remains a separate action. Promoting one held request does not resume the rest of the held queue.

An explicit promotion that encounters an existing per-thread dispatch waits for that dispatch to release its lock, then re-reads the original durable row. A bounded deduplicated wake set avoids waiting for periodic queue maintenance; it introduces no new polling timer. Promotion during a metadata-only queue read obtains a bounded recent active-turn identity before steering. A definitive native no-active-turn rejection permits a new turn only after a fresh matching idle read on the same transport. A different active turn or lost acknowledgement is not automatically retried.

Client actions capture their original source, credential generation and navigation incarnation. Original acknowledged outbox state may be retained after navigation, while error presentation and draft/editor callbacks stay on their originating view. A delayed response cannot repaint another conversation or a newly opened incarnation.
